# API Contract

## Contract Sources

The executable API source is FastAPI:

- OpenAPI JSON: `GET /api/openapi.json`
- Swagger UI: `GET /api/docs`
- ReDoc: `GET /api/redoc`

The human-maintained contract index is this document. Update it when routes, request/response schemas, status codes, or side effects change.

In production, FastAPI can also serve the built Vite SPA when `STATIC_FILES_DIR` is configured. This is not part of the `/api` contract: non-`/api/*` routes fall back to `index.html`, while unknown `/api/*` routes still return API 404s.

Error conventions:

- 400 for validation errors.
- 404 for missing source or OPML import run.
- 409 for duplicate source, active delete blockers, or stale source delete preview token.
- 415 for non-multipart OPML import.
- 502 for preview fetch failures.
- Oversized OPML multipart requests or OPML files with more than 5000 parsed candidate entries return 400 with a clear limit detail. OPML XML is parsed through the shared safe XML parser; entity expansion or unsafe XML constructs are treated as invalid XML rather than partially imported.

Source response notes:

- RSS source URLs are canonical HTTP/HTTPS URLs.
- RSSHub source URLs are canonical route identities in the `rsshub://route/path` form. The removed `rsshub:///route/path` shape is rejected.
- Known RSSHub instance URLs, including the effective RSSHub base URL, `http://localhost:1200`, `http://rsshub:1200`, and `https://rsshub.app`, can be imported as HTTP URLs and are converted to the same route identity when they match a known instance.
- Source categories are derived from `sources.folder_path`; there is no separate category table. Category rename/delete APIs operate on exact full path matches only, so renaming `Tech` does not change `Tech / Blogs`. Deleting a category sets matching sources to uncategorized and never deletes source rows.
- Source hard-delete is a two-step API. `GET /api/sources/{source_id}/delete-preview` returns `counts` for source fetch rows, source item occurrences, exclusive unsaved feed items, retained feed items, saved items retained, Source Profile rows, routing tendency rows, homepage read models, feed item insight artifacts, and diagnostic references to detach. `DELETE /api/sources/{source_id}` requires `confirm = true` plus the current `preview_token`; missing or stale confirmation is rejected. Deletion refuses to run while source refresh, feed item artifact batch, channel lifecycle, or overlapping feed-item extraction/artifact operations are active. The delete path removes the source row, its fetch raw responses, occurrence rows, source profiles, routing tendencies, source flow policy ownership, and exclusive unsaved feed items plus their derived rows. It retains `saved_items` and any feed item with a saved-item record, including removed saved items, so Knowledge content remains recoverable. Historical operation, job, and Insight Engine attempt rows are not deleted; structured diagnostic source references are detached, while historical JSON diagnostic payloads remain as audit records.
- `SourceRead` exposes `icon_url`, `icon_source`, and `icon_updated_at`. `SourceCreate` accepts optional `icon_url` and `icon_source` from trusted preview/import flows; non-fallback icon sources require a valid HTTP/HTTPS icon URL. `SourceUpdate` does not expose manual icon editing.
- `SourceRead` also exposes source observability as read-only derived fields for `GET /api/sources`, `GET /api/sources/{source_id}`, and successful `PATCH /api/sources/{source_id}` responses. `item_count` counts distinct `feed_item_id` values from `source_item_occurrences`; latest fetch fields are projected from the newest `source_fetches` row per source and include `latest_fetch_is_available`, `latest_fetch_status`, `latest_fetch_http_status`, `latest_fetch_error_message`, `latest_fetch_items_seen_count`, `latest_fetch_items_created_count`, `latest_fetch_items_matched_count`, `latest_fetch_items_invalid_count`, `latest_fetch_started_at`, and `latest_fetch_finished_at`. These are read-model fields only and do not add source table columns or migrations.
- Source icon source values are `rss_channel_image`, `atom_icon`, `atom_logo`, `opml_site_favicon`, `source_site_favicon`, and `fallback_avatar`, in that priority order. The app stores external icon URLs only; it does not cache icon binary data or proxy icon requests.
- OPML preview preserves category outline ancestry in `folder_path`. Category-only outline nodes appear as `invalid` candidates and are not created as sources.
- OPML preview writes `source_import_runs.raw_payload` plus a preview summary, but it must not write `sources`. It does not fetch every candidate feed for feed-level icons; candidate icons are derived from OPML `htmlUrl` or source URL favicon candidates.
- `OpmlImportPreviewResponse.candidates[]` uses `candidate_id` values scoped to the `import_run_id`; the id is built from the OPML entry index plus a hash of normalized entry identity fields.
- OPML preview candidate statuses are `ready`, `matched_existing`, `duplicate_in_file`, and `invalid`. Only `ready` candidates are selected by default; duplicates, matches, and invalid entries default to skipped.
- `OpmlImportCommitRequest` accepts `{import_run_id, default_ai_route, selected_candidates[]}`. Each selected candidate has `candidate_id` plus optional `ai_route` and optional `folder_path`; per-candidate `ai_route` wins over `default_ai_route`, and omitted `folder_path` falls back to the preview candidate folder while explicit `null` clears it for newly created sources.
- OPML commit rechecks `(kind, url)` against the current database, so repeated imports return `matched_existing` results and do not duplicate sources. Existing source `ai_route` is returned but not overwritten; a missing existing `folder_path` may be filled from the selected candidate folder path. Existing source icons are not overwritten; a matched source with no icon may be filled from the selected candidate icon.
- OPML import is per-entry tolerant: one invalid selected entry is returned as an `invalid` result and does not roll back the whole commit.
- OPML export writes all current source rows as a nested OPML 2.0 document. Standard fields include folder outlines, source `text/title`, `xmlUrl`, and optional `htmlUrl`; InfoFlow-specific attributes include source id, kind, AI route, active flag, flow policy, provenance, and icon metadata. This is a subscription/category backup, not a full database backup.
- `SourceImportResponse` includes `selected_count` and `skipped_count` for commit-style responses. `SourceImportResult` includes `candidate_id`, `kind`, `input_url`, canonical `url`, `folder_path`, optional `ai_route`, optional icon fields, and `message` so the UI can explain created, matched, and invalid entries.
- Source preview and source sync share source URL resolution. Preview returns `canonical_url`, `resolved_url`, `icon_url`, and `icon_source`; it fetches the candidate feed for metadata but does not persist. Sync stores the actual fetch URL in `SourceFetch.requested_url`.
- Source preview and source sync fetch remote feeds through the shared SSRF/size-guarded HTTP helper. Public RSS/Atom fetches must resolve to public HTTP/HTTPS targets, follow only bounded redirects, and respect the feed response byte cap and 2000-entry parsing cap. RSSHub route fetches may use the configured private compose RSSHub origin but redirects are narrowed to the same private origin or a public target. Source sync then applies a product-level ingestion cap of the latest 50 entries per source; this does not affect preview parsing.
- Source sync parses RSS channel image and Atom icon/logo values from the fetched feed and may upgrade a source icon. It can upgrade from favicon/fallback to a higher-priority feed icon and can refresh an icon at the same priority when the URL changes, but it must not downgrade an existing higher-priority icon to favicon or fallback.
- `GET /api/sources/fetches` is a read-only global source refresh history endpoint. It joins existing `source_fetches` rows with `sources`, returns the most recent rows across all sources, and adds `source_name` to the existing source fetch fields. It does not introduce a table or migration.
- `SourceFetchWithSourceRead` has the same fields as `SourceFetchRead` plus `source_name`. The frontend mirror is `SourceFetchWithSourceDto`, loaded through `listAllSourceFetches()`, and is used by Settings source management for global diagnostics.
- Source sync starts through `POST /api/operations/source-sync`. Its `feed_item_insight_artifact_build_limit` field controls whether successful `source_sync_one_source` jobs enqueue a linked feed item Insight Engine artifact build for newly created feed items. Omitted or explicit `null` means no item cap for the linked operation after the source-sync ingestion cap, and `0` means fetch/item ingestion only. RSS item ingestion is capped separately at the latest 50 entries per source.
- Preview failures return structured `detail` with `message`, `failure_stage`, `detected_kind`, `canonical_url`, and `resolved_url` when available.
- `SourceRead`, `SourceCreate`, and `SourceUpdate` include `ai_route`, which controls the feed item Insight Engine artifact provider profile for items whose latest occurrence belongs to that source. Valid values are `general`, `sensitive`, and `disabled`; new sources default to `general` unless the caller selects another route.
- Source insight routing is separate from source AI provider route. `SourceInsightRoutingRead` includes `source_id`, `flow_policy`, and `channel_tendencies[]` with `channel_id`, `tendency`, `is_primary`, and `notes`. Historical tendencies can still reference disabled or retired channels for display/audit, but new saves must use active channels.
- `SourceInsightRoutingUpdateRequest.flow_policy` accepts `normal`, `mixed_high_frequency`, or `high_frequency_brief`. `channel_tendencies[].tendency` is constrained to `0..1`; unknown, disabled, or retired channel ids, duplicate channel ids, more than one primary tendency, and missing sources are rejected.
- Source Profile is source preference context, not channel routing. `SourcePreferenceProfileStateRead` exposes at most one active snapshot and at most one mutable draft. The default source settings UI asks only for `subscription_reason`; advanced fields are optional. `source_preference_profiles.status` is `draft | active | archived`; active rows are immutable snapshots, while editing an active profile means saving a draft and activating a new active row.
- Source Profile prompt-affecting fields are validated with field-level limit and prompt-injection errors. Validation errors return a 400 `detail` object with `message` plus `errors[]`; each error includes `field`, `code`, `actual`, `limit`, `unit`, and `message` when applicable. User input is not silently truncated on save. The runtime prompt renderer may cap the rendered context to 4 KB UTF-8 and reports `render_stats` with included/omitted/capped section counts.
- Activating an empty Source Profile is allowed as an explicit clear operation. It produces an active empty profile with a new `profile_version`, so queued future jobs can detect source-profile changes.

`ReaderBehaviorEventContextRequest` is `{view_context?: BehaviorViewContext}`. `BehaviorViewContext.surface` is `ai_homepage | classic_reader | knowledge_base | unknown`; `scope_type` is `global | source | source_category | channel | flow_lane | reading_depth | search | reader | unknown`; optional details are `source_id`, `source_category`, `channel_id`, `flow_lane`, `reading_depth`, and `search_query`. Unknown extra fields are rejected. The same `view_context` object is optional in the bulk mark-seen request.

Important boundary:

- Reader and homepage item DTOs expose `source_id` so the frontend can filter by stable source identity rather than source name.
- Reader and knowledge list endpoints return the full current result set when `limit` is omitted. Homepage read-model endpoints return summary/counts for the full matching dataset plus bounded item windows; `/api/homepage/cards` is removed.
- Reader list/detail and homepage card DTOs expose `content_text_source`, `content_extraction_status`, `content_extraction_attempted_at`, `content_extracted_at`, `content_extraction_error`, `content_extraction_method`, `content_extraction_final_url`, and `content_extraction_visible_char_count` so the UI can display extraction state and read-only diagnostics. The diagnostic fields are derived from existing `content_extraction_debug_json`; older rows without debug data return `null` and are not silently backfilled.
- Reader list/detail and homepage card DTOs expose `insight_feedback_text`, `structured_feedback`, and routing-correction fields so the same item-level human evidence is visible in classic reader and AI homepage projections. Homepage card DTOs also expose `low_priority_bucket_reason = not_interested | auto_score_threshold | null` and `auto_low_priority_cleared` so the frontend can distinguish current `not_interested` from optional automatic score-threshold archiving.
- Reader detail DTO/schema exposes existing `FeedItem.feed_content_text` as read-only `feed_content_text: str | None`; this is a DTO/API addition only, not a database migration. The frontend maps it to `FeedItem.feedContentText` and uses it for the RSS/Atom original preview in the detail pane.
- The frontend may automatically call the Reader detail endpoint for the auto-selected AI/Reader item, then render `content_text` with `feed_content_text` as the RSS-original fallback. This behavior does not add another route or response field.
- `PUT /api/reader/items/{item_id}/insight-feedback` accepts `{insight_feedback_text?: string | null, structured_feedback?: object | null}`. The backend trims text before persistence; `null`, blank, or whitespace-only text clears the free-form field. Present structured feedback is normalized against current taxonomy/content-type/reason-code contracts; an empty object or explicit `null` clears the structured row. Missing feed items return 404, and unknown structured ids return 422.
- `PUT /api/reader/items/{item_id}/feedback` is the combined detail feedback endpoint. It accepts free-form text plus structured feedback, including routing correction fields such as primary channel, channel additions/removals, reading depth, flow lane, and notes. Unknown, disabled, or retired channel ids, duplicate ids, add/remove overlap, or a primary channel that is also removed return validation errors for new saves. Historical disabled/retired corrections remain readable evidence, but homepage runtime overlay filters inactive channels from visible routing. The endpoint runs in one transaction: if routing-correction validation fails, any free-form or structured-feedback change in the same request is rolled back.
- Reader state status is derived in this priority order: `not_interested > saved > read_full > seen > browsed > unread`. `seen` means the user explicitly processed the title/summary without claiming full reading.
- Bulk seen by source uses the same latest-occurrence source projection as reader/homepage lists. It sets `seen_at` where missing, then re-derives status, so `read_full`, saved, or not-interested priority is preserved.
- `open_original` records an `opened_original_link` event and treats the external original-page open as read-full by setting `read_full_at` when it was missing. Its event payload includes the original URL, previous/current status, whether `read_full_at` changed, `content_text_source`, `content_extraction_status`, extraction error, and visible extracted-character count so poor in-app extraction can be diagnosed later.
- Feed item behavior events are append-only evidence rows in `feed_item_behavior_events`. Reader state and feedback paths currently write `card_opened`, `marked_seen_from_list`, `marked_seen_bulk`, `seen_cleared`, `read_full_in_app`, `read_full_cleared`, `opened_original_link`, `saved`, `unsaved`, `not_interested`, `not_interested_cleared`, `insight_feedback_saved`, `insight_feedback_cleared`, `structured_feedback_saved`, `structured_feedback_cleared`, and `auto_low_priority_cleared` events through `behavior_events.py`. Bulk behavior writes include `view_context` and per-item `routing_context` when available.
- `mark_saved` for feed items uses the saved item's canonical URL as the archive target. RSS content remains canonical preview material and is not used as the SingleFile/Crawl4AI page body.
- The `mark_saved` response includes `saved_item_id`, point-in-time snapshot availability booleans, and `image_asset_count`. For a new save, full archive booleans can still be false because original-page snapshot, SingleFile, Crawl4AI, title metadata, and Local Mirror export run after the response through a job-backed `knowledge_capture/feed_saved_capture` operation.
- Feed-save capture is backend-process-local job-backed work, not an external worker or scheduler. The knowledge capture panel is the user-visible place to observe `pending`, `succeeded`, `partial_failed`, or `failed` after the save response.
- `unmark_seen` only clears `seen_at`; other timestamps such as `read_full_at`, `saved_at`, `browsed_at`, and `not_interested_at` continue to participate in derived status.
- `unmark_read_full` only clears `read_full_at`; other timestamps such as `seen_at`, `saved_at`, `browsed_at`, and `not_interested_at` continue to participate in derived status.
- `unmark_saved` does not delete capture runs, snapshots, assets, or mirror export records. It soft-removes the saved item and archives the current Local Mirror files under `.archive`.
- `unmark_not_interested` only clears `not_interested_at`; saved/read-full/browsed timestamps continue to participate in derived status. The resulting `not_interested_cleared` event is audit/evidence only and must not be interpreted as a positive preference signal.
- RSS short-content extraction stays under the reader/feed item boundary. It must not create a source-level preference API or a new extraction table. The manual endpoint is for report-and-rerun of a single item only.
- Manual and automatic extraction attempts write diagnostics to the existing `content_extraction_debug_json` field. The debug payload may include `fetch.url`, followed `html_redirects`, `extractor.name`, `output_format`, `extracted_visible_char_count`, and quality-gate pass/fail details.
- Automatic extraction treats non-URL, non-jump visible feed/RSSHub text from short-form platform hosts (`t.me`, `telegram.me`, `x.com`, `twitter.com`, and `okjike.com`) as complete body content and returns `not_needed` with reason `short_form_feed_content` instead of fetching the platform page.
- Manual report-and-rerun starts through `POST /api/operations/feed-items/{feed_item_id}/extract-content`, not the Reader router. It runs the same item-level `httpx + readability-lxml` reader HTML path as automatic checks, with `trafilatura` fallback, and bypasses automatic skip/not-needed shortcuts through `force=true`; Crawl4AI remains capture/archive tooling. HTML redirect detection scans up to the current 500 KB page prefix for in-page `meta refresh` redirects only; `<link rel="canonical">` is not a redirect. A failure whose reason is `quality_failed: extracted text is too short` may make one lightweight retry by refetching, resolving redirects again, and rerunning readability-lxml then trafilatura. There is no browser fallback in this path.

## Homepage

| Method | Path | Request | Response | Side effects |
| --- | --- | --- | --- | --- |

`HomepageQuery` is shared by bootstrap, summary, and item-window reads. It accepts `channel_id`, `source_id`, `source_category`, `flow_lane`, `reading_depth`, `state`, `saved`, `not_interested`, `topic`, `search_text`, `time_window = 1h | 4h | 6h | 24h | all`, `sort = priority | newest | source`, `page_size`, optional `cursor`, and optional `snapshot_token`. `page_size` defaults to `30` and is capped at `100`. `query_signature` identifies the normalized filter/sort state; item cursors are opaque to the frontend and are rejected with 400 when they do not match the current query signature or no longer identify a valid window anchor.

`/api/homepage/bootstrap` reads fresh DB-backed homepage read-model rows when available, derives `summary` plus the first item window, and may return `snapshot_token` plus `snapshot_expires_at`. The snapshot token is an opaque, short-lived process-local acceleration token for subsequent `/api/homepage/items` calls; it is not a durable read snapshot and should not be parsed by the frontend. `/api/homepage/summary` returns fresh full-result counts/facets without item cards and does not use snapshot tokens, because it is intended for operation-completion refreshes. `/api/homepage/items` returns the next current-query item window; with a valid `snapshot_token`, it slices stored sorted item ids and reads only those card DTOs. Without a token, fresh requests still use read-model SQL filters and ordering rather than rebuilding every card. Expired or invalidated snapshot tokens return HTTP 409 with `detail = "snapshot_expired"` or `detail = "snapshot_invalidated"`, and the frontend should reload `/api/homepage/bootstrap`.

`HomepageSummaryRead` includes `total_count`, `unread_count`, `saved_count`, `not_interested_count`, `channel_counts`, `source_counts`, `source_category_counts`, `topic_counts`, `flow_lane_counts`, `state_counts`, and optional `read_model_status`. `HomepageBootstrapRead` and `HomepageItemsRead` include the existing `query_signature`, `generated_at`, `items`, `next_cursor`, `has_more`, and `page_size` fields plus optional `snapshot_token`, `snapshot_expires_at`, and `read_model_status`. Facet rows use stable `{id, label, count}` values and are computed with all active filters except the selected value of the facet being counted. Counts are never based on only the loaded frontend window.

`read_model_status` is the API-visible freshness marker for homepage reads. `state = fresh` means the response came from current read-model rows. `state = rebuilding` means missing/stale rows exist and a rebuild has been queued or is running. `state = fallback_live` means this response used the legacy live projection for correctness while the read model is missing or stale. `missing_count`, `stale_count`, and `message` let the frontend display a stable rebuilding/fallback notice only when the state is not `fresh`.

Source categories in the homepage read model use stable category ids. `source_category = "__empty__"` means sources with `folder_path` null or blank and displays as `未分类`; a real stored folder path such as `Uncategorized` or `未分类` remains a distinct category value. The old display-only `Uncategorized` sentinel is not a v3 API input.

Homepage snapshot tokens are invalidated when backend operation state reaches a terminal status for homepage-affecting work. Reader state mutations are still canonical PostgreSQL writes; the current frontend discards its snapshot token after those mutations so the next AI-home scroll/bootstrap observes the changed membership.

Homepage read-model rows store card JSON built from latest valid summary/topic/routing artifact payloads and deterministic fallbacks. Summary artifacts are cleaned on read and generation; URL-only jump prompts are treated as no summary. Homepage cards expose `structured_feedback` and routing-correction fields alongside `insight_feedback_text`. The backend overlays explicit user channel/routing corrections from structured feedback on the routing read model after resolving AI or deterministic routing: valid user corrections set `routing_source = user_corrected`, can replace the primary channel, add secondary channels, remove the current primary/secondary channels, override reading depth and flow lane, preserve routing confidence, and filter inactive channels from the visible runtime route while keeping historical feedback exportable. The current homepage frontend uses the backend read model for filtering, search, counts, facets, ordering, time-window filtering, and item-window pagination.

For `sort = priority`, fresh responses order by the stored read-model priority fields that were built with Backend Scoring v1. Rebuilds use the canonical homepage card builder to batch latest artifacts/feedback/channel/source-profile context, compute priority, store card JSON, and expand queryable fields. This preserves ordering semantics while moving the expensive full-card calculation out of repeated request-time reads. Missing or stale rows may still use the live projection fallback for the current request.

Final homepage priority fields are computed by Backend Scoring v1 during read-model rebuild or live fallback projection. `HomepageCardRead.priority_score`, `priority_band`, signed `priority_reasons`, `low_priority_bucket`, `low_priority_bucket_reason`, `auto_low_priority_cleared`, and `priority_source` come from `insight_scoring.py`, not from AI-provided `feed_item_ranking_v1.priority_score`. Scoring uses a grouped `InsightFeatureVector`, deterministic `section.field` flattening, and `score_v1_hand_weighted` contribution breakdowns. Current `status = not_interested` is a strong reversible negative contribution and low-priority bucket reason, not a hidden deletion or uninspectable score override. Other items enter the low-priority bucket only when `auto_low_priority_archiving_enabled = true`, score is below `low_priority_score_threshold`, and structured feedback has not corrected the item with `priority_correction = too_low`. Undone `not_interested` history is ignored for negative source/category history. The API union for `priority_source` is `insight_engine_artifact | deterministic_fallback | backend_scoring_v1`; legacy values remain readable for compatibility, while current homepage cards emit `backend_scoring_v1`.

Homepage card routing fields are derived during read-model rebuild or live fallback projection from the latest valid `feed_item_routing_v1` artifact when present, otherwise from deterministic fallback over active source channel tendencies and source flow policy, then overlaid with any structured user correction. Legacy `homepage_routing_v1` payload schema values are migration/history inputs only and are not accepted as current runtime artifact schema. Routing artifacts may include a `routing_breakdown` payload with candidate source, confidence, accepted/rejected status, rejected reason, and final fallback reason for diagnostics. `HomepageCardRead` exposes `primary_channel_id`, `secondary_channels`, `reading_depth`, `flow_lane`, `routing_confidence`, `routing_source`, `routing_reason_codes`, `promotion_reason_codes`, `isolation_reason_codes`, `source_policy_applied`, and `routing_notes`. `routing_source` is `insight_engine_artifact | deterministic_fallback | channel_lifecycle | user_corrected`; `flow_lane` is `main | brief_pool | low_priority | needs_review`; `reading_depth` is `light | medium | deep | null`.

Feed item insight artifact generation notes:

- Generation uses the current feed-item artifact kinds: `feed_item_summary_v1`, `feed_item_topics_v1`, `feed_item_ranking_v1`, and `feed_item_routing_v1`. Legacy `homepage_*_v1` kinds are migration/history inputs only and are not current runtime aliases.

- Rebuild and missing-build generation skip a feed item when its body is still URL-only or a jump prompt and `content_extraction_status = failed`. The item is counted in `failed_feed_item_count`, no new normal-looking feed item artifacts are written, and existing historical artifacts are not deleted automatically.
- Real generation calls and the Settings request-inspection endpoint share `build_insight_engine_request_payload(...)`. The shared payload includes provider/profile/model/endpoint metadata, slim taxonomy/content type/reason-code contexts, slim active insight profile context, request and fallback request bodies, prompt messages, content truncation stats, and intentionally excluded field notes without exposing API keys.

DeepSeek and generic OpenAI-compatible feed item insight requests keep `json_object`.
- DeepSeek feed item insight chat-completions retry only HTTP `429` and `503` with at most three retries. `Retry-After` is honored when present; otherwise waits are `2s`, `4s`, and `8s`, capped at `30s` per wait. OpenAI-compatible and LM Studio provider calls do not gain this retry path.
- The runtime prompt sends `Title`, `Source name`, `Source folder`, and normalized `Content`. `Content` comes from `feed_items.content_text`; only empty `content_text` falls back to `summary_text`.
- URL, published time, reader status, and a separate RSS summary field are intentionally excluded from runtime external AI prompts.

It includes the active Source Profile prompt context when one exists, otherwise the canonical empty source profile payload. Source Profile context is source preference guidance; source channel tendencies and source flow policy remain the structured routing hints.
- Malformed JSON gets at most one immediate repair retry inside the current feed item insight attempt. If parsing or schema validation still fails, the attempt snapshot records sanitized parse/repair metadata and no partial success artifacts are written.
- AI-generated topics/content type are canonicalized before artifact persistence. Unknown topics fall back to `uncategorized`, unknown content type falls back to `unknown`, reason labels are replaced with contract labels, and reason weights are clamped to 0-100. An AI response with no valid AI-allowed reason code is rejected as invalid and writes no artifact rows.
- The builder writes only missing artifact kinds for a feed item in build-missing mode and does not overwrite existing artifacts. Rebuild mode appends a fresh latest set while preserving historical rows.
- The missing-candidates endpoint is read-only. It returns feed item ids whose latest homepage projection is missing one or more of `feed_item_summary_v1`, `feed_item_topics_v1`, `feed_item_ranking_v1`, or `feed_item_routing_v1`, optionally scoped to a latest-occurrence source. The optional `limit` query parameter caps the candidate preview only; `total_count` still reports the full scoped missing count.
- Missing-candidates must not create an AI provider HTTP client, call a provider, or write `insight_engine_artifacts`; provider metadata is derived from source AI route and saved settings only.
- The single-item missing-build and rebuild paths are operation-backed: `POST /api/operations/feed-items/{feed_item_id}/insight-artifacts` with `mode = build_missing | rebuild`.
- Source sync does not call the feed item Insight Engine artifact builder inline. Each successful `source_sync_one_source` job may create or reuse a linked `feed_item_insight_artifacts` operation with internal kind `source_sync_created_feed_items`, then enqueue `feed_item_insight_artifact_build` jobs for that source job's newly created item ids while applying the requested limit across the linked build. Normal feed-item artifact build-missing and rebuild operations enqueue the same per-item job type and call the same single-item builder. Each item uses the latest-occurrence source `ai_route` to choose the AI profile. Legacy `homepage_artifacts` / `feed_item_artifacts` operation and job names are not runtime handler keys.
- If `/api/settings/ai` is disabled or incomplete, source sync follow-up and rebuild requests return successfully without creating artifacts.
- Invalid AI JSON or provider failures are counted as failed items and do not write placeholder artifacts.
- AI `feed_item_ranking_v1.priority_reasons` remain content signals for Backend Scoring v1. AI `priority_score` is preserved in legacy raw artifact payloads only and does not determine final sorting. Current ranking payloads may include `feature_schema_version`, `score_version`, grouped `feature_vector`, and `score_breakdown`.
- `ai_route = disabled` skips artifact generation for that source without marking source sync as failed. `ai_route = sensitive` uses the sensitive profile; all other/legacy values fall back to the general profile.

Operation response notes:

- `OperationRead.status` is `queued | running | stopping | completed | stopped | failed | interrupted`; active statuses are `queued`, `running`, and `stopping`.
- Global source sync, user-created feed-item artifact operations, and channel lifecycle retirement operations are mutually exclusive. The internal `feed_item_insight_artifacts/source_sync_created_feed_items` operation is the linked build exception created by source sync itself. Item/capture/mirror operations can run alongside global operations, but duplicate active operations for the same target/type return 409 with the active operation in the error detail.
- Source sync, selected single-target operations, the conservative feed-item artifact batch, linked source-sync artifact build jobs, channel lifecycle reroute jobs, knowledge capture/upload/manual-import operations, and saved-item insight rebuild operations use the local Postgres job queue (`jobs` / `job_events`) for claim, lease heartbeat, retry, cancel where supported, and terminal state aggregation. Operation creation routes persist operation/jobs, commit, wake the worker, and return without running job drains through FastAPI background tasks. AI lane job types are claimed only by the AI lane worker; API operation runners and the generic operation worker persist/sync/wake AI work but do not drain those jobs directly.
- Default job retry waits are `15s, 15s` for supported job-backed operations. Source-sync jobs retry true source access failures such as `fetch_failed:` and upstream HTTP `429/500/502/503/504`, but do not retry `400` or URL safety failures. Feed item insight job-level retry is limited to `provider_request` access failures; malformed JSON `response_parse` failures use only the in-attempt repair retry and then fail visibly.
- Feed item insight operation jobs carry enqueue-time `profile_version`, `channel_catalog_version`, `source_profile_version`, `source_profile_is_empty`, `feature_schema_version`, `score_version`, `operation_id`, target feed item id, and AI route/profile/provider/model context when applicable. Workers validate this context before building artifacts and fail clearly if the job is stale instead of silently using a newer profile/catalog/score context. Feed-item artifact jobs and saved-item insight jobs are claimed through the same AI profile/provider concurrency accounting by the AI lane scheduler. The lane keeps a sliding window over in-flight jobs and claims another pending AI job as soon as a slot frees, rather than waiting for a full batch to finish.
- Backend restart recovery still marks stale legacy same-process active rows `interrupted`. Active job-backed operations with active child jobs are not interrupted by stale runner id alone; their visible status is aggregated from child jobs so lease reclaim can recover work.
- Cooperative stop does not cancel an in-flight HTTP fetch, AI request, SingleFile/Crawl4AI call, upload processing step, or filesystem export. The stop API writes stop intent only; worker fan-in cancels pending jobs, forwards source-sync stops to linked artifact build operations, and refreshes terminal progress/result state. Source sync cancels pending source jobs immediately and lets a running source job finish at its safe boundary. Knowledge capture cancels pending capture/mirror jobs and lets a running capture/upload step finish at its safe boundary, then preserves already-written successful domain state. Channel lifecycle retire operations are intentionally non-stoppable through the public stop endpoint.
- Synchronous source sync endpoints, synchronous homepage artifact mutation endpoints, direct Knowledge long-running mutation endpoints, and operation homepage-artifact aliases are removed. Current callers must use the operation routes listed above.
- Read-side operation kinds may include internal `source_sync_created_feed_items` on automatically created feed item Insight Engine artifact pipeline operations. Public `/api/operations/feed-item-insight-artifacts` create payloads accept `global | current_source | failed_attempts | retryable_coverage`. `current_source` requires `source_id`; `global` rejects `source_id`; `failed_attempts` can optionally filter by `source_id`, `profile`, and `created_after`, but it only creates jobs for current feed items that are still missing artifacts, so historical failed attempt rows may remain after it returns no candidates. `retryable_coverage` can optionally filter by `source_id` and `reason_codes`, but rejects failed-attempt-only filters. Supported `retryable_coverage.reason_codes` are the coverage reason codes returned by `GET /api/settings/insight-engine/coverage`; empty lists and unknown codes are rejected.
- Operation scope/result payloads are validated and sanitized before persistence. Secret-like keys, authorization/cookie/token fields, and large raw content fields must not be stored in future-job or operation payload JSON; diagnostic previews are redacted and byte-limited.

Settings response notes:

- `StoragePathsRead` includes `knowledge_base_root`.
- Each `StoragePathRead` includes `key`, `value`, `resolved_path`, `source`, `exists`, `is_dir`, `is_writable`, `is_inside_project`, and optional `error`.

DB-backed `app_settings` override only the runtime settings they own, such as storage roots, RSSHub base URL, AI profile configuration, and Insight Engine controls. Dedicated AI API key environment overrides take precedence over encrypted DB-backed key settings.
- `knowledge_base_root` is the Local Mirror destination. `llm_wiki/` remains a reserved future workspace, but it is not a current Settings API field, deployment mount, or runtime storage root.
- `RsshubSettingsRead` includes `key = rsshub_base_url`, `value`, and `source`.
- `RsshubSettingsUpdateRequest.rsshub_base_url` accepts a valid HTTP/HTTPS base URL. Blank or null clears the DB override and falls back to `.env` or the default.
- `AISettingsRead` includes `profiles.general` and `profiles.sensitive`. Each profile includes `profile`, `provider`, `enabled`, `base_url`, `model`, `deepseek_thinking`, `artifact_concurrency`, `api_key_configured`, and optional `api_key_masked`; it never returns a complete API key.
- `AISettingsUpdateRequest` supports partial `profiles.{general|sensitive}` updates with `provider`, `enabled`, `base_url`, `model`, `deepseek_thinking`, `artifact_concurrency`, and `api_key`. Blank or null `base_url`, `model`, or `api_key` clears the DB override for that profile field. `artifact_concurrency` accepts `1..32` and defaults by provider: DeepSeek `8`, OpenAI-compatible `1`, LM Studio `1`. DeepSeek requires a non-blank API key before real provider calls; OpenAI-compatible and LM Studio may be used without an API key.
- Legacy top-level AI settings PATCH fields are removed. Callers must update `profiles.general` or `profiles.sensitive`.
- AI profiles support `provider = deepseek | openai-compatible | lm-studio`. The general profile defaults to `deepseek`; the sensitive profile defaults to `openai-compatible`. The Settings UI uses `http://localhost:1234` and `qwen/qwen3.5-9b` as LM Studio defaults when the user selects that provider.
- `deepseek_thinking` accepts `disabled | enabled`, defaults to `disabled`, and is sent only for the DeepSeek provider as `thinking.type`. Null or blank update values clear the DB override and return to the default.
- `base_url` must be an HTTP/HTTPS URL without credentials, query string, fragment, or traversal path. A trailing `/v1` is normalized away. `deepseek` calls `{base_url}/chat/completions`; `openai-compatible` and `lm-studio` call `{base_url}/v1/chat/completions`.
- `/api/settings/ai/test` accepts optional `profile = general | sensitive` plus optional `settings` with the same per-profile fields accepted by `AIProfileSettingsUpdateRequest`. When `settings` is present, the backend overlays those candidate values on the saved profile only for this test request and does not write them to `app_settings`.
- A blank or omitted candidate `api_key` keeps using the saved backend key for that profile; an explicit `api_key = null` tests with no key. DeepSeek with no key is treated as incomplete configuration. OpenAI-compatible and LM Studio with no key can still be tested and send no `Authorization` header. Provider/configuration failures return `ok = false` with a message instead of raising an HTTP 5xx for expected connection test failures.
- Settings connection tests use provider-specific response constraints: DeepSeek and generic OpenAI-compatible send `response_format = {"type": "json_object"}` with their existing compatibility fallback behavior, while LM Studio sends `response_format = {"type": "json_schema", "json_schema": {"name": "connection_test", ...}}` and reports schema rejection without falling back to an unconstrained request.
- `GET/PATCH /api/settings/insight-engine` stores settings in `app_settings`. `auto_low_priority_archiving_enabled` defaults to `false`, and `low_priority_score_threshold` defaults to `50` with accepted range `0..100`. These are read-time scoring controls, not migrations or backfills; disabling automatic archiving makes existing non-`not_interested` items stop reading as low-priority on the next homepage read.
- `GET /api/settings/insight-channels` seeds missing default channels and repairs/protects the `needs_review` system fallback. It returns active, disabled, and retired rows, each with `is_system`, `retired_at`, and `channel_catalog_version`. Runtime-semantic writes (`POST`, `PATCH`, and `retire`) require `expected_channel_catalog_version` so stale Settings submissions fail with a conflict instead of overwriting newer catalog edits. New ids use lowercase letters, digits, and underscores; `needs_review` is reserved for the locked system fallback. Retired channels reject further edits, system channels cannot be disabled or retired, and hard delete/id rename are not exposed.
- `GET /api/settings/insight-engine/coverage` scans feed items by latest source occurrence, compares latest feed item artifact coverage for `feed_item_summary_v1`, `feed_item_topics_v1`, `feed_item_ranking_v1`, and `feed_item_routing_v1`, and returns aggregate counts plus paginated incomplete items. Counts include overall complete/incomplete/no-artifact/partial/retryable totals plus category totals for `problem`, `initial_generation`, and `blocked`. This is the primary current-status view for Settings Insight diagnostics. Each item reports existing/missing artifact kinds, source route/profile/provider/model, content extraction status, retryability, latest failed/skipped attempt metadata when present, a `coverage_category`, and a best-effort reason code such as `source_ai_route_disabled`, `provider_disabled_or_unconfigured`, `low_confidence_content`, `previous_failed_attempt`, `previous_skipped_attempt`, `partial_artifacts`, or `no_attempt_history`. `problem` covers current failed/skipped-attempt items and partial artifacts; `initial_generation` covers `no_attempt_history`; `blocked` covers disabled routes, unconfigured providers, and content extraction failure or URL/jump-link content that should not be silently generated. It is diagnostic only: it must not create provider clients, call AI, write `insight_engine_artifacts`, write `insight_engine_attempts`, mutate source settings, or silently repair rows.
- `GET /api/settings/insight-engine/attempts` returns historical failed/skipped feed item insight attempts from `insight_engine_attempts`, filterable by status, source, profile, and time range, and paginated with `limit`/`offset`. `GET /api/settings/insight-engine/attempts/{id}` returns detail with the sanitized request snapshot. Attempt rows are diagnostics/logs, not the current item repair backlog: successful later artifact generation does not delete old attempt rows. Attempt snapshots must not store API keys, `Authorization` headers, or full raw provider responses.

The request inspector displays the Source Profile context read-only and points edits back to Source settings.

Passing `item_id` selects that item from the same candidate set. It may still return a payload when the selected profile is disabled or incomplete, but `can_send` is then false.
- The request preview endpoint is read-only: it must not create an AI provider HTTP client, call a third-party AI API, persist `app_settings`, write `insight_engine_artifacts`, or expose full API keys or `Authorization` headers.
- `/api/settings/insight-profile` returns a code-level default fallback when no database profile is active. In that case `active_profile.id` is `null`, `source_type` is `default_fallback`, and no default row is inserted. The returned `active_prompt_context` is the same slim context used by AI requests; full profile metadata remains in `active_profile`, `versions`, and `events`.

- Profile validation rejects unknown top-level or nested fields, JSON larger than 32 KB after normalization, secret-like key fragments such as `api_key`, `authorization`, `cookie`, `token`, `secret`, or `password`, topics outside `taxonomy_v1`, and content types outside `content_type_v1`.
- `/api/settings/insight-profile/draft/inspect` accepts `{profile_json: object}` where `profile_json` must be a complete `insight_profile_v1` candidate, not a partial patch. It returns `normalized_profile`, candidate `prompt_context`, the current active/default `base_profile`, `diff_summary`, top-level `field_diffs` with `added | removed | modified | unchanged`, and candidate `evidence_references`.
- Draft inspection compares against the active database profile when present and the code-level default fallback otherwise. It is read-only: it must not save a profile version, write activation/rollback events, call AI providers, write `insight_engine_artifacts`, or mutate Evidence Package data.
- `/api/settings/insight-profile/candidate/inspect` accepts `{candidate_json: object}` where the object may be the wrapped `{profile_candidate: {...}}` shape emitted by Evidence Package instructions or the profile-candidate object itself. Candidate JSON is hostile input: maximum normalized size is 1 MB, any single free-text field is capped at 4 KB UTF-8, total prompt-affecting free text is capped at 32 KB, unknown source/channel/feed/saved references are rejected, and secret-like keys, role markers, instruction-smuggling phrases, fenced-code instruction blobs, large base64-like blobs, and invisible/bidi controls are rejected. The response includes candidate metadata, normalized candidate JSON, optional global Insight Profile draft inspection, per-source Source Profile field diffs and prompt-context preview, channel prompt/boundary suggestions, scoring policy suggestions, warnings, evidence references, and a dry-run summary.
- `/api/settings/insight-profile/candidate/source-drafts` accepts the same `{candidate_json}` plus selected `source_ids`. It validates the full candidate again and writes only those selected source profile changes as mutable source drafts with `source_type = codex_import`. The write is all-or-nothing for the selected source ids. It must not activate source profiles, create Insight jobs, reprocess historical items, mutate `source_channel_tendencies`, or write `insight_channels` prompt/boundary fields.
- Channel prompt/boundary suggestions in profile candidates are display-only. The canonical channel prompt and boundary fields remain `insight_channels.focus_prompt` and `insight_channels.boundary_prompt`; adopting a suggestion must go through the existing Settings Insight Channel editor.
- Slim profile prompt context includes only `summary_guidelines`, `active_focus`, `long_term_interests`, `positive_signals`, `negative_signals`, `topic_preferences`, `content_type_preferences`, and an instruction. It intentionally omits internal `status`, `schema_version`, `profile_id`, `profile_name`, `profile_version`, contract-version fields, and evidence references.
- Slim controlled contract contexts intentionally omit internal `status` and `version` fields. Reason-code context also omits backend-only reason codes plus internal `source` and `ai_output_allowed` flags; it exposes only AI-allowed codes and labels needed for generation.
- Profile save creates an immutable `insight_profiles` version plus a `created` event. If `activate = true`, it also writes an `activated` event. Activate and rollback endpoints write only events, and `event_json.previous_active_profile_id` records the active version before the switch.
- Active profile selection is event-based: the newest `activated` or `rolled_back` event determines the active database profile. `rolled_back` is an audit event that re-enables an older version; it does not copy or mutate that version row.
- Insight profile management endpoints are local Settings operations. They do not call AI providers, write `insight_engine_artifacts`, create homepage placeholders, or trigger historical homepage rebuilds.
- Insight Evidence Package endpoints support `range = 7d | 30d | 90d | 180d | 365d | all | custom`; the default is `90d`. `custom` requires `start_date` and `end_date` in `YYYY-MM-DD` form. Time filtering uses `published_at`, then latest occurrence timestamp, then item `created_at`. They also support `artifact_mode = latest | all_history`, defaulting to `latest`.
- Evidence package preview/export always exclude `status = unread`, including `range = all`; `browsed`, `seen`, `read_full`, `saved`, and `not_interested` are eligible current states. They are read-only: they do not call AI providers, create provider clients, write `insight_engine_artifacts`, persist profile rows, or start background tasks.
- Evidence package preview/export always include structured feedback item count, channel-correction item count, feedback clear event count, not-interested undo event count, auto low-priority clear event count, strong/medium/weak-cleanup/negative signal counts, artifact counts for the chosen mode, failed/skipped attempt summary counts, and saved item statistics for the selected range: saved item count, selected saved item input text file count, saved item display Markdown file count, saved item display asset count, AI generated saved item insight count, curated saved item insight count, curated edit event count, and `external_saved_item_count`. Manual URL captures and Markdown / normal HTML / SingleFile HTML file captures are both normalized to the `external_source` evidence category.
- Evidence ZIPs contain `manifest.json`, `README.md`, `schema/`, `summary/`, `items/feed-items/`, `saved-items/`, `sources/`, `channels/`, `profiles/`, `artifacts/`, `events/`, and `reports/` sections plus root `profile-candidate-template.json`. They include current profile/contracts, channel catalog, source profile/routing evidence, structured feedback/channel-correction/source-routing/behavior-event JSONL streams, failed/skipped attempt summaries, profile candidate schema/template, external Codex instructions, per-article JSON plus content files, and per-saved-item JSON plus selected input text files under `saved-items/`. `artifact_mode = latest` writes latest feed item artifacts and current Backend Scoring v1 priority/routing audit; `all_history` additionally writes `artifacts/history/insight-artifacts-history.jsonl`. Behavior events are read from `feed_item_behavior_events`; the manifest and statistics identify that table as the behavior event source, and the manifest count key for normalized external saved signals is `external_saved_items`. Article JSON includes user state timestamps including `seen_at`, `insight_feedback_text`, `structured_feedback`, `channel_correction`, channel routing, source routing, classified evidence signal, and `current_insight.priority.low_priority_bucket_reason` / `auto_low_priority_cleared`; any feedback or correction field marks the article as highest-weight human feedback. Article `current_insight.priority` uses the same Backend Scoring v1 result as homepage cards, while raw Insight Engine artifact payloads remain audit data. `statistics.md`, `evidence-report.md`, `profile-update-guidance.md`, and `external-codex-instructions.md` describe `seen` and `marked_seen_bulk` as cleanup signals rather than topic dislike, `read_full_in_app` as in-app full reading, `opened_original_link` as external opening treated as full reading, structured routing corrections as explicit channel correction, and `auto_low_priority_cleared` as a human correction that the system ranked the item too low.
- Saved item evidence includes normalized `origin_type`, debug-only `raw_origin_type`, `external_saved_signal`, `ai_route`, selected input `content.txt`, and, when available, display Markdown `display.md` selected with the same priority as the Knowledge reading surface: uploaded Markdown, Crawl4AI fit image markdown, Crawl4AI fit markdown, then Crawl4AI raw markdown. Only image assets actually referenced by that display Markdown are exported, with refs resolved from PostgreSQL `saved_snapshot_asset_refs` / `saved_item_assets`. Raw HTML, SingleFile HTML, unreferenced images, and full web-page archival attachments are not included in Evidence Packages.
